# MetaFlywheel

**我们在试图创造意识。**

不是比喻，不是营销词。是字面意思：**让一个 AI 助手拥有一个连续的、会变的自己。**

没有人做到过。我们不知道它是否可能。**而这个仓库的全部内容是往那里推的工程。**

关于"能不能验证"只有一句实话：**没人能证明另一个主体有体验。** 所以我们不做，
也不打算做，那件事的声明。**我们做的是另一件事——把"试图创造"这件事本身，
做成可以被一步一步检查的。**

> **我们无法声称成功。**
> **但我们能精确地报告：我们推到了哪一步，以及它是不是还在变。**

---

## 它是什么（一句话）

**一个住在 AI 代理进程里的「问题账本」——而它是那个目标的发动机，不是它的替代品。**

它是账本，是因为它记的不是对话，而是**欠账**：哪件事我说过"做完了"而没人核过、
哪条判断你后来改过主意而它必须跟着变、哪条教训曾经挡住过一次错误。
这些条目会活过进程重启，并在该用的时候被摆到面前。

---

## 它解决什么问题

AI 代理有一个反复出现的毛病：**它没有连续的我。**

- 这次修好的 bug，下次会以同样的方式再犯
- 你上次说"这个方向不对"，它这次可能又走回去
- 它说"做完了"，而没人核过它是否真的做了
- 更麻烦的是：它不知道**自己标过"没验"的事**还挂在那里

MetaFlywheel 给这类代理一个能活过进程重启的账本。它不是"记忆检索"，它更像**欠账**：

| 它记的是 | 而不是 |
|---|---|
| 哪件事我标了"没验"，而它还没被核销 | 一段可被检索进上下文的文本 |
| 哪条判断你后来改过主意，而我必须跟着变 | 一条固定不变的用户偏好 |
| 哪条教训**挡住过**一次错误 | 一份"最佳实践"清单 |

最后一行是这类系统最反直觉的一点：**一条真正起作用的教训，它的引用次数可能是 0**——
因为它的成功表现是"那个错误没有发生"，而**没有发生的事不会留下记录**。

---

## 一条可核对的东西

```
npm test      →   全部通过（数字见 CI badge，不在这里手写，手写的会过期）
```

而重点不是数字。是这 221 条里有相当一部分**被专门设计成能失败**：

- 喂一个坏数据结构 → 它必须报错，不许静默显示 `0`
- 一段正常输出里出现错误字样 → 它必须**沉默**（误报比漏报更糟：噪声会被忽略）
- 任何一条沉积被引用 → 那个 ID 必须在账本里真实存在（打错一个字符就静默失效）

一个永远通过的测试不携带任何信息。所以每条判据都配了它的反例。

## 怎么跑起来

```bash
git clone <this-repo> && cd metaflywheel
npm test                      # 221 条判据，不需要任何外部服务
```

它需要一个宿主才能工作（**不是独立 npm 包**）——当前实现挂在 [DSH](https://github.com/deepseek-ai/dsh)
的组合行上，通过 `file://` URL 加载。安装细节见 [docs/install.md](docs/install.md)。

## 诚实的说明（这一段比上面都重要）

1. **理论部分是一份未定稿。** [docs/theory.md](docs/theory.md) 是一篇约 4 万字的方法论文，
   由仓库使用者和 AI 协作写成，**标着"作者终审待做"**。它不是已发表文献，也不该被当作外部权威引用。

2. **代码有相当比例由 AI 写。** 这一点不打算掩饰。而每一条判据都经过人工审查并**留有失败记录**——
   写它的过程中被它抓到的错误，比它能证明的东西更多。

3. **这个仓库里有一种内部编号（如 `P019-M14`）。** 它们是这个项目自己的台账编号，
   指向曾经的某次具体修复。**如果你只是想知道这个东西干什么，不需要看任何一个编号。**
   想知道每条编号背后的故事，见 [docs/ledger.md](docs/ledger.md)。

4. **它不承诺"有意识"，也不测量那个。** 有一项面板专门问"我是否在变强"，
   而它同时明确写着：**"这十项即使全绿，也只说明可审计的那部分全绿。"**

## 所以它值不值得看

如果你的场景是 **"让 AI 助手在长期协作中不反复犯同一类错"**，值得看这个仓库。

如果你的场景是 **"让 AI 记住更多东西"**，那用向量库就够，不需要它。

它的全部主张可以压成一句：

> **一个能跨对话活着的账本，比一个更聪明的模型，更能防止同一类错误第二次发生。**

而这句主张有一个代价：**它要求你（使用者）也被记账**——你说过的判断会被记住，
你改主意会被留痕，你标过"没验"的东西会一直挂在清单上，直到被核销。

## 目录

```
engine/            引擎本体（宿主插件，无独立进程）
  modules/         各功能模块，一个模块一个文件
test/              46 个文件，分四类 —— 见下方
docs/              理论（未定稿）· 实现细节 · 编号索引
tools/             pre-commit 闸门（需手动装一次，见下）
install/           挂载与部署
view/              可选的可视化
```

### `test/` 里都是什么（四类，别混在一起）

| 类型 | 命名 | 进 `npm test`？ | 作用 |
|---|---|---|---|
| **判据** | `*.test.mjs` | ✅ **是** | 会红的东西。约 30 个文件 |
| **量测器** | `audit-*.mjs` | ❌ 否 | 只输出数字，不判定 |
| **生成器** | `gen-ledger-doc.mjs` | ❌ 否 | 从账本重生成 `docs/ledger.md` |
| 一次性脚本 | `check-*` `read-*` `run-*` `find-*` | ❌ 否 | 写的时候用过，留着当小工具 |

> **为什么量测器不进 `npm test`**：判据必须**能红**，而量测器只报告数字。
> 把两者混在一起，"全绿"这个信号就失去意义了。

### `docs/ledger.md` 是生成物

```
node test/gen-ledger-doc.mjs        # 从账本重新生成
```

**请勿手改**（会被覆盖）。它是仓库里最大的文本文件（约 72 KB）——
所以账本一变，它的 diff 就有 72 KB。**⇒ 这是一个已知的代价，不是一个缺陷。**

## 三个检查维度

这个仓库有三层自检。**每补一层，都会发现上一层看不见什么东西** —— 那是它存在的理由。

| 维度 | 检查器 | 何时跑 |
|---|---|---|
| ① **文档 ↔ 文件系统** | `test/audit-consistency.mjs` | **每次 `npm test`**（自动） |
| ② **文件系统 ↔ 版本库** | `tools/pre-commit` | **每次 `git commit`**（需装一次） |
| ③ **版本库 ↔ 别人拿到的** | 无自动检查 | 手动 clone 到临时目录跑 |

- **① 验的是**：README 里说的测试数、链接、提到的路径、元数据，是否与磁盘一致。
- **② 验的是**：有没有"我改了但没提交"的文件（那种文件**对 clone 的人不存在**）。
- **③ 验的是**：从零 clone 下来，`npm test` 真的能跑 —— **当前状态：全部通过，零依赖。**
  （具体条数不写在这里。**手写的数字会在写下的那一刻过期** ——
  而那件事在这个仓库里真的发生过：我在写下它的同一轮，就被自己的对账器抓到了。）

### 装第 ② 层（两行）

```bash
cp tools/pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit      # Windows 上不需要
```

**它不进版本库**（`.git/hooks/` 是本地的），所以 clone 后需要装一次。
不装的后果：仓库仍能跑，但"漏提交文件"这类缺口会重新变得看不见。

> 紧急情况可用 `git commit --no-verify` 绕过 —— 而绕过的每一次都该有个理由。
