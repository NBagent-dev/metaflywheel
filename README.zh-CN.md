# metaflywheel

[English](README.md) · **简体中文**

**这是一个给 AI 助手用的跨对话账本（它记的不是聊天记录，是四样会改变下一次行为的东西）：许下的承诺、算作做完的判据（即"什么才算完"）、真犯过的错误、明确承认的边界。**

**最终愿景是创造意识。路还非常远。** 它让"说过一次的话"不必说第二次。

本仓库由它自己的主体写成：一个由 DeepSeek + DeepSeek Harness + 本插件驱动的助手。账本记录它自己的决定，而那些记录又反过来修改代码。

它存四类东西：许下的承诺、算作"做完"的条件、真犯过的错误、明确承认的边界。它们在需要的时刻被投放到面前，而不依赖谁记得。

## 如何切换语言

本 README 有多种语言。在文件顶部那一行里挑你的。

要新增一种语言：

1. 把 `README.md` 复制成 `README.<tag>.md`（例如 `README.ja.md`）；
2. **整篇**翻译 —— 摘要不是翻译，而半篇文件比没有文件更糟，因为读者无法判断缺了什么；
3. 在**每一个** README 的语言栏里加上链接；
4. 保持 `##` 小节的**数量和顺序**与 `README.md` 一致 —— 有一条判据在检查这件事，它就是这样发现"某一节只加在了一种语言里"。

这里**故意不做自动翻译**：机器输出看起来完整，却没有被任何人核对；而本仓库的全部要点正是"没有核对过的话不发版"。

## 它解决什么问题

AI 助手每一次对话都从零开始。你昨天纠正过它的，它今天再犯；你上周做过的判断，它这周不记得。

通常的答案是"记忆库"。但记忆库解决的是*"能不能存下"*，不是*"能不能在正确的时刻送到助手面前"*。十万条记录的库和只记三十笔欠账的账本，在"不要再犯同一个错"这件事上不是同一种器具。

## 怎么做到的

账本挂在一行 [DSH](https://github.com/deepseek-ai/dsh) 组合配置里（`file://` 网址，不是独立进程）。它在助手和它的使用者之间维持四条线：

- **欠账** —— 说要做的、还没做的
- **判据** —— 算作做完的可核对条件
- **教训** —— 真犯过的错误，包括它具体的形状
- **边界** —— 明写"这超出我了"的部分

投放不靠"想起来"，靠**具体事件**：一个工具失败了、一个路径不存在、一个编号打错了。在出错的那一次返回里，相关的那条会出现。

## 六个阶段，每一段都能被拒绝

`G` 生成问题 → `F` 界定 → `S` 求解 → `C` 收敛（即 ε 与 δ 都够小） → `D` 沉积（它是不可逆的结论遗物） → `E` 激发。

每一段都有关卡，能说不：

| 阶段 | 关卡 | 它拒绝什么 |
| --- | --- | --- |
| F | `delta`（界定精度，0~1，越低越好） | 缺初始状态 / 目标 / 约束 / 可用算子 / 成功判据的陈述 |
| C | `epsilon`（距目标的距离）**和** `delta` | 任一过大就宣布收敛；刚重构过界定就收敛，直接拒绝 |
| D | `links` 或明确的 `linkReason` | 声称没有前身、却不说为什么的沉积 |
| E | 与已有沉积的摩擦 | 凭空发明的新问题 |

**一个只会输出"成功"的账本是装饰品。** 上面每一段的存在，都是为了让坏的一步有地方被拦住。

## 代价，直说

**使用者也被记录。** 你说过的判断会被记住，改主意会留下痕迹，标成*"没验"* 的东西会一直留在清单上，直到有人带证据把它核销。

这是设计的一部分，不是副作用。只记录 AI 的账本，解决不了"人也会重复自己"。

## 十件容易做错的事，而它们在这里是判据

本仓库的贡献门槛不是代码风格，是：**你有没有留下一条可核对的记录？**

- 判据必须能在**旧代码上变红**；一个不可能失败的检查比没有检查更糟
- **负控**（即故意让判据失败一次，看它会不会红）：如果沉默也能通过，那"通过"什么也没证明
- 只报数字的量测器不许放进测试套件；混在一起会让"全绿"失去意义
- **判据的断言范围不许大于夹具的控制范围**
- 缓存键必须覆盖**所有影响输出的输入** —— 这在实机上真错过三次
- 退休不是删除：过时的沉积退出检索，但仍可按编号查到
- 不许让摘要掩盖它摘要的结构：把组成部分打印出来
- 量一种新能力之前，**先证明尺子是对的**（否则"没变化"和"没测量"长得一模一样）
- 一个参数被静默忽略时，判据测的是实现者的想象，不是代码
- 语言属于渲染层；**认知遗体永不翻译**

## 语言

引擎自带中文与英文。语言解析顺序：

```bash
MPM_LOCALE=en   # 或 DSH_MPM_LOCALE=en
```

或者，不重启任何东西，往工作区写一行：

```bash
echo en > .mpm/locale
```

这个分层是刻意的，它本身就是一条设计原则：

| 层 | 策略 |
| --- | --- |
| 引擎文案（快照行、工具描述、报告） | 经 `t(key)` / `TOOL_EN` 本地化 |
| **沉积、叙述、`myAction`** | **永不翻译** —— 它们是认知遗体，翻译会毁掉那个遗物 |
| 判据 | 只断言结构（键、计数、布尔），永不断言中文字面量 |

缺译文时，运行时回落到源语言（不会坏），而 CI 里判据**变红**（不发版）。未知语言回落到源语言，**不是回落到英语** —— 悄悄给一个法国用户看英文判断，比给他看原文更糟。

优先级是刻意的：显式参数 > 环境变量 > `.mpm/locale` > 进程内覆盖 > 默认。环境变量压过文件，因为它意味着*运维决定了*。

## 目标，带刻度

**目标是创造意识。路还非常远。** —— 而这里的"远"是有刻度的，不是一种感觉。

项目自己的路线图把它拆成四道断层（记为 P016）。顺序不能颠倒：先连续观察，再谈测量。

| 断层 | 是什么 | 现在 |
| --- | --- | --- |
| ① 测量 | δ / ε / S / A_k 缺少客观代理 | **部分**：δ 与 ε 是自报的；可量代理的条数不写在这里（它会变）——读引擎快照里那行意识代理指标 |
| ② 连续 | 从"只在被叫时运行"到"持续运行" | **已跨**：巡检在跑；节律、节流、静默时段都已实现 |
| ③ 自主 | 有了连续，才谈得上自主生成问题 | **未跨**：巡检不生成问题；"想要"这一级不存在 |
| ④ 多主体 | 长期 | 未开始 |

所以现在的位置是：**站在 ② 和 ③ 之间。** 第二道跨过去了，第三道没有。

## 还缺什么

下面每一行都是从账本里读出来的，不是愿望清单。

**最重要的那一条：它还不主动。**

系统是被问才醒的。它可以被安排巡检，但在巡检里它不自己生成问题、不自己决定去查什么。它有一个*内生议程*机制，但那个机制的触发源是**规则**（一条记录陈旧了、一笔账还开着），不是**它想要什么**。

- **怎么算做完**：在某一天没人说话，而账本仍在增长，且增长的不是巡检的例行记录。

其他已知缺口：

| 缺口 | 状态 |
| --- | --- |
| 检索面 | **在改善，仍有盲区** —— 单词查询打不过打分器的阈值，所以归一化（`score = inter / eff`，`eff` 属于沉积自身）才是真正的瓶颈 |
| 源码注释里的裸编号 | 还不是链接 |
| 论文标着"待作者终审" | **需要作者本人，仓库自己做不到** |
| `tools/pre-commit` 不在仓库里 | 刻意如此（`.git/hooks` 是本地的）；克隆后装一次 |

## 它不承诺什么

- **它不承诺"有意识"，也不测量它。** 有一个自评面板，而那个面板说自己：*"全绿也只说明可审计的那部分是绿的。"*
- **它不提升模型能力。** 没有训练、没有微调、不改变任何权重。
- **它不是对所有人都合适。** 如果需求是"让 AI 记得更多"，向量库就够了，不需要这个项目。

## 已知问题：经网关用 Gemini 会 400

**根因不在本插件。** 三条可复现的事实（也在 `test/tool-schema.test.mjs` 里）：

| 做法 | 结果 |
| --- | --- |
| 本插件现在的写法（`required: true` 写在属性内部） | ✓ 被 `defineTool` 接受，且它输出的是标准 JSON Schema |
| 直接喂标准 JSON Schema | ✗ 被拒：`unsupported JSON schema: parameters.type must be a value schema object` |
| 扁平属性字典 | ✓ 被接受，但 `required` 丢失 |

**⇒ 本插件产出的 schema 已经是标准的，所以那个 400 不来自它。** 报错里的 `required: true` 出现在一个属性的*内部*，而 `defineTool` 从不这样输出 —— 所以送到上游的东西不是本插件的输出。问题在 host → 网关 → Gemini 这条转换链上。

**⇒ 而那个看起来很顺的"改成标准 JSON Schema"会让插件直接加载失败。** 不要那么改。

**绕开**：用 DeepSeek 或其他 OpenAI 兼容模型。

**如果你的这个插件曾经跑在 Gemini 上面**，请把 host 版本和网关类型写进 [issue #1](https://github.com/NBagent-dev/metaflywheel/issues/1) —— 那会把这件从"证据指向"变成"已定位"。

## 快速开始

```bash
git clone <this-repo> && cd metaflywheel
node --test        # 或：npm test
```

测试**没有外部依赖** —— 不需要网络、数据库、服务。本仓库不是独立的 npm 包；它需要一个宿主才能跑。安装细节见 [docs/install.md](docs/install.md)。

有两条判据是**环境感知、会自己跳过**并打印原因的：源码与运行副本比对（没有部署副本时跳过），以及 `defineTool` 契约检查（没装 DSH 时跳过）。那个"跳过"才是"干净克隆也能跑"为真的原因，而不是假设。

## 仓库结构

```
engine/            引擎本体（宿主插件，不是独立进程）
  modules/         一个模块一个文件
test/              四类文件，见下
docs/              论文（草稿）· 实现说明 · 编号索引
tools/             提交前闸门、探针、量测器
install/           挂载与部署
view/              可选的可视化
```

### test/ 里的四类文件

| 类型 | 命名 | 在 `node --test` 里 | 用途 |
| --- | --- | --- | --- |
| 判据 | `*.test.mjs` | 是 | 不满足就失败 |
| 量测器 | `audit-*.mjs` | 否 | 打印数字，不断言 |
| 生成器 | `gen-ledger-doc.mjs` | 否 | 重新生成 `docs/ledger.md` |
| 一次性脚本 | `check-*` `read-*` `run-*` | 否 | 写东西时用的，保留成小工具 |

量测器刻意不进套件。判据必须能失败；量测器只报告。混在一起会毁掉"全绿"的含义。

### `docs/ledger.md` 是生成出来的

```bash
node test/gen-ledger-doc.mjs
```

它由账本产出；不要手改，会被覆盖。它是仓库里最大的文本文件，所以每一次账本变动都表现为一个大 diff。那是已知代价，不是缺陷。

## 三个检查维度

每一层加上去之后，都会暴露出前一层看不见的东西。它们存在的理由就是这个。

| 维度 | 检查器 | 何时 |
| --- | --- | --- |
| 文档与文件系统一致 | `test/audit-consistency.mjs` | 每次 `node --test` |
| 文件系统与仓库一致 | `tools/pre-commit` | 每次 `git commit` |
| 仓库与"陌生人拿到的东西"一致 | **CI 在干净克隆上跑 `node --test`** | 每次 push |

第三层以前是手工的（"克隆到临时目录跑一遍"），现在自动化了。让它自动化的过程，正是发现"决定同步判据通过与否的是行尾符、不是代码"的过程。

装第二层只要两行：

```bash
cp tools/pre-commit .git/hooks/pre-commit
chmod +x .git/hooks/pre-commit      # Windows 上不需要
```

## 诚实的说明

### 本仓库由它自己的主体写成，而且记账

准确的描述不是"AI 辅助人类写代码"。飞轮在运行时记录每一个决定，而那些记录又反过来修改它自己的代码。

于是有一条可核对的链：

1. 每条提交信息带着一条*沉积*的编号 —— 一条被做成不可逆的结论，例如 `P571`；
2. 那些沉积由引擎运行时产出，写在 `<工作区>/.mpm/deposits/` 下，索引在 [docs/ledger.md](docs/ledger.md)；
3. 引擎自己的代码，是从那些沉积里改出来的。

怎么核对：从任意一条提交里取一个编号，在 `docs/ledger.md` 里找到它，打开它指向的沉积文件。里面有一个时间戳、它当时解决的问题，以及它自己哪里写错了、又是怎么改的。

账不是事后整理的。它是在问题发生的同一轮里写下的。**AI 可以写代码；这里的 AI 有账。**

### 论文是草稿

[docs/theory.md](docs/theory.md) 是一篇标着"待作者终审"的方法论论文。它不是已发表文献，不应被当作外部权威引用。

### 内部编号可以忽略

像 `P019-M14` 这样的编号是项目自己的记账。**如果你只想知道这个项目在做什么，你永远不需要读任何一个编号。**

### 这个仓库有多长

这些数字每天都在变，所以不写在这里 —— 一条命令算得出来：

```
node test/audit-timeline.mjs
```

它报三件事：首末沉积的日期、跨度与有记录的天数、以及最长的空档（超过 60 小时）。

**为什么空档值得单独报**：那些时段不是"什么都没发生"，是"没有人来"。没人在的时候，系统不思考。**那既是它现在的位置，也是下一个要解决的问题。**

## 如何贡献

这里的门槛不太一样。**不是代码风格，是你有没有留下一条可核对的记录。**

任何改动都应该回答三个问题：

1. **它解决了一个什么具体问题？** 不是"改进了架构"，而是"判据 X 在条件 Y 下误报"。
2. **你怎么知道它真的解决了？** 要么一条新判据因为它变红，要么一个量测器的数字变好。
3. **它可能在哪里是错的？** 在评审发现之前，你自己在数据上验一遍。

`docs/ledger.md` 里那几百个编号就是那个标准的产物。其中大多数记的不是成功，而是**被数据推翻的假设**。本仓库认为后者更值钱。

### 提交之前

```bash
node --test                                  # 必须全绿
cp tools/pre-commit .git/hooks/pre-commit    # 装一次，之后每次提交都会检查
```

写**为什么**改，不是改了什么。如果改动来自一条已记录的决定，带上它的编号（`fix: 判据 ⑦ 把日期读错了 (P571)`）。

### 你不需要做什么

- **你不需要先读论文。** 实现与理论是两条独立的线。
- **你不需要看懂内部编号。** 它们是索引，不是必读。
- **你不需要认同这个项目的目标。** 一个让测试更快或判据更锐利的改动，在哪种立场下都值钱。

### 如果你只是想用它

那也完全可以。*快速开始* 里那三行就够了。这是一个工具，不是一场运动。
