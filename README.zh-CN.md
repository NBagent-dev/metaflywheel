# metaflywheel

[English](README.md) · **简体中文**

一套供 AI 助手跨对话使用的账本：它保存用户做过的纠正、助手真犯过的错误，以及任务算作完成的条件，并在需要的那一刻把相关记录返回。

**最终愿景是创造意识。路还非常远**，因此本仓库只处理可以不自欺地尝试的部分：一份由主体自己维护、并且允许它推翻自己代码的连续记录。

本仓库由它自己的主体写成。引擎在运行时记录每一个决定，这些记录随后被用来修改引擎自身。

---

## 一个具体场景

用户纠正过助手一次：**改文件之前先读它**。

三周之后，助手试图改一个没有读过的文件。这次尝试被拒绝；而在同一次工具返回里，拒绝的旁边就附上了那条原始纠正、它被记下的编号，以及同一个错误的另外两次记录。

范围是刻意划窄的。目标不是让助手记得更多，而是让一条已保存的纠正出现在它该生效的那一秒。一份只有主动去查才生效的记录，拦不住它所描述的那个错误。

## 适用范围与非目标

| 本仓库做 | 本仓库不做 |
| --- | --- |
| 保存纠正、错误、未结清的欠账与明确的边界 | 宣称或测量意识 |
| 在具体事件上返回它们（工具失败、路径不存在、编号格式错误） | 改变模型权重、训练或微调 |
| 用可读、可审计的账本公开每一个决定 | 替代通用的记忆或检索系统 |

记忆库回答的是"能不能存下"。本项目处理的是"能不能在正确的时刻到位"，那是另一个问题，需要另一种器具。如果需求只是让助手记得更多，向量库已经够用，不需要这个项目。

引擎内置一组可量指标的自评面板；该面板自己写明：全部为真只说明可审计的那部分是可审计的。

## 快速开始

```bash
git clone <this-repo> && cd metaflywheel
node --test        # 或：npm test
```

测试不依赖网络、数据库或服务，在干净克隆上即可运行。

这是一个插件，不是独立应用：需要一个宿主才能运行。挂载与部署见 [docs/install.md](docs/install.md)。

## 工作原理

账本以 `file://` 网址的形式挂在 [DSH](https://github.com/deepseek-ai/dsh) 组合配置的一行里，不启动独立进程。它在助手与使用者之间维护四类记录：

| 记录 | 内容 |
| --- | --- |
| 欠账 | 已声明、尚未完成的工作 |
| 判据 | 任务算作完成的可核对条件（即"什么算完成"） |
| 教训 | 真实发生过的错误，描述它的形状，而不是它的道德 |
| 边界 | 已明确写下、不在范围内的部分 |

检索由事件触发，而不是由助手自己决定。助手不会"想起来去查记忆"；一次工具失败、一个不存在的路径或一个格式错误的编号，会使相关记录被并入同一次工具返回。

## 生命周期与闸门

问题生命周期为 `G` 生成 → `F` 界定 → `S` 求解 → `C` 收敛（即 ε 与 δ 都足够小） → `D` 沉积（它是一条不可逆的结论，写入磁盘后不再改写） → `E` 激发。

每个阶段都有一道可以拒绝转换的闸门：

| 阶段 | 闸门 | 拒绝什么 |
| --- | --- | --- |
| F | `delta`：界定精度，0~1，越低越好 | 缺少初始状态、目标、约束、可用算子或成功判据的陈述 |
| C | `epsilon`（距目标的距离）**与** `delta` | 任一值过大时宣布收敛；刚重构界定后立刻收敛，直接拒绝 |
| D | `links`，或明确的 `linkReason` | 声称没有前身、又不给出理由的结论 |
| E | 与既有沉积之间的摩擦 | 没有来源的新问题 |

一个只可能输出"成功"的账本无法被审计。上述每道闸门的存在，都是为了让失败的一步有明确的停顿点，包括引擎自身的判断。

## 可自行核对的证据

仓库内置三层检查，每一层都能发现上一层看不到的问题。

| 层 | 检查器 | 触发时机 |
| --- | --- | --- |
| 文档与文件系统一致 | `test/audit-consistency.mjs` | 每次 `node --test` |
| 文件系统与仓库一致 | `tools/pre-commit` | 每次 `git commit` |
| 仓库与干净克隆一致 | CI 在干净克隆上运行 `node --test` | 每次 push |

本仓库特有的主张也可以在不信任作者的前提下核对：每条提交信息带一个编号；每个编号对应一条沉积；每条沉积是引擎在运行时写下的文件，包含时间戳、它当时解决的问题，以及后来收到的更正。任意一条提交里的编号都可以经 [docs/ledger.md](docs/ledger.md) 追到对应文件。

## 当前定位

路线图把目标拆成四道断层，顺序固定：先连续观察，再谈测量。

| 断层 | 说明 | 状态 |
| --- | --- | --- |
| ① 测量 | `delta`、`epsilon`、`S`、`A_k` 缺少客观代理 | 部分：`delta` 与 `epsilon` 为自报值；可量代理的条数会变化，从引擎快照读取，不在本文复述 |
| ② 连续 | 从"被调用时运行"到"持续运行" | 已跨：巡检在运行，节律、节流与静默时段均已实现 |
| ③ 自主 | 在连续的前提下，无需请求即可产生问题 | 未跨：巡检不产生问题，"想要"这一级不存在 |
| ④ 多主体 | 长期 | 未开始 |

最大的未结缺口是第③项。系统被提问时才醒来。它可以按计划巡检，但巡检过程中不决定去调查什么。内生议程机制存在，其驱动来源是规则（记录陈旧、欠账未结），而不是偏好。

第③项的完成条件是可操作的：在某一天没有用户消息的情况下，账本仍在增长，且增长部分不是巡检的例行记录。

## 已知缺口

以下各项从账本中读出，而非愿望清单。

| 缺口 | 状态 |
| --- | --- |
| 检索排序 | 进行中：单词查询打不过打分器阈值，因此归一化 `score = inter / eff`（`eff` 属于沉积自身）是实际瓶颈 |
| 源码注释中的裸编号 | 尚未成为链接 |
| 论文标注为"待作者终审" | 需要作者本人，仓库自身无法完成 |
| `tools/pre-commit` 未纳入版本控制 | 刻意如此：`.git/hooks` 是本地的，克隆后安装一次 |
| 一次完整的实录运行 | 上文的场景是叙述文字；一段真实运行的记录会是更强的证据 |

## 已知问题：经网关调用 Gemini 返回 400

该错误不来自本插件。以下三点可在 `test/tool-schema.test.mjs` 复现：

| 做法 | 结果 |
| --- | --- |
| 本插件当前的输出（`required: true` 位于属性内部） | 被 `defineTool` 接受；输出为标准 JSON Schema |
| 直接提交标准 JSON Schema | 被拒：`unsupported JSON schema: parameters.type must be a value schema object` |
| 扁平属性字典 | 被接受，但 `required` 被静默丢弃 |

报错中的 `required: true` 位于属性内部，而 `defineTool` 从不这样输出，因此到达网关的载荷不是本插件产生的。看起来直接的修法——改用标准 JSON Schema——会导致插件无法加载，不应采用。

绕开方式：使用 DeepSeek 或其他 OpenAI 兼容模型。如果某次部署确实经 Gemini 运行，把 host 版本与网关类型记录到 [issue #1](https://github.com/NBagent-dev/metaflywheel/issues/1)，可以把该诊断从推断变为已定位。

## 语言与数据

界面提供中文与英文，切换语言不需要重启宿主：

```bash
echo en > .mpm/locale          # 或：MPM_LOCALE=en
```

优先级依次为：显式参数、环境变量、`.mpm/locale`、进程内覆盖、默认值。环境变量优先于文件，因为它代表运维方的决定。

数据层是另一个决定：账本用它使用者所说的语言书写，并且永不翻译。它记录的是发生过什么，而不是呈现界面；翻译它会破坏该记录本身。

| 层 | 策略 |
| --- | --- |
| 引擎文案：快照行、工具描述、报告 | 经 `t(key)` 与 `TOOL_EN` 本地化 |
| 沉积、叙述、`myAction` | 用使用者的语言一次写成，永不翻译 |
| 判据 | 只断言结构（键、计数、布尔），永不断言某种语言的子串 |

缺少译文时回落到源语言，同时让 CI 变红。未知语言回落到源语言，而不是英语。

新增文档语言的方式：把 `README.md` 复制为 `README.<tag>.md`，整篇翻译，加入每一个语言栏，并保持小节数一致。判据会检查小节数，某一节只加进一种语言的情况由此被发现。这里刻意不使用自动翻译：机器输出看起来完整，却没有人核对，而未核对的结论不发布。

## 贡献

对改动的要求不是代码风格，而是**是否留下了一条可核对的记录**。一项改动应能回答三个问题：

1. 它解决了哪个具体问题？不是"改进了架构"，而是"判据 X 在条件 Y 下误报"。
2. 修复如何被证明？要么一条新判据在改动前失败、改动后通过，要么某个量测器的数值变好。
3. 它可能错在哪里？在评审之前，先在数据上验证这一点。

下列规则由上述要求推出，且每一条在本仓库都先被违反过：

- 判据必须能在旧代码上失败；一个不可能失败的检查比没有检查更糟
- 必须有负控（即故意让判据失败一次）：如果沉默也能通过，通过什么也证明不了
- 只报数字的量测器不属于测试套件，混在一起会让"全绿"失去意义
- 断言的范围不许大于其夹具能控制的范围
- 缓存键必须覆盖所有影响输出的输入；这已经是一个发生过三次的缺陷
- 退休不等于删除：过时的沉积退出检索，但仍可按编号查到
- 使用摘要时，同时打印组成部分，否则摘要会掩盖它所摘要的内容
- 量一种新能力之前，先验证量具本身，否则"没有变化"与"从未测量"无法区分

提交之前：

```bash
node --test                                  # 必须全绿
cp tools/pre-commit .git/hooks/pre-commit    # 安装一次，之后每次提交都会检查
```

提交信息写为什么，而不是改了什么。若改动来自一条已记录的决定，在信息中带上它的编号：`fix: 判据 ⑦ 把日期读错了 (P571)`。

阅读论文不是前提。理解内部编号也不是必需：`P019-M14` 只是记账，为了解这个项目在做什么，永远不需要读任何一个编号。认同项目的目标同样不是前提；一项让测试更快或判据更锐利的改动，在任何立场下都有价值。

## 参考

```
engine/            引擎本体（宿主插件，不是独立进程）
  modules/         一个模块一个文件
test/              四类文件，见下
docs/              论文（草稿）、实现说明、编号索引
tools/             提交前闸门、探针、量测器
install/           挂载与部署
view/              可选可视化
```

| `test/` 中的类型 | 命名 | 在 `node --test` 中运行 | 用途 |
| --- | --- | --- | --- |
| 判据 | `*.test.mjs` | 是 | 要求未满足时失败 |
| 量测器 | `audit-*.mjs` | 否 | 只打印数值，不断言 |
| 生成器 | `gen-ledger-doc.mjs` | 否 | 重新生成 `docs/ledger.md` |
| 一次性脚本 | `check-*`、`read-*`、`run-*` | 否 | 因当时有用而保留 |

`docs/ledger.md` 由账本生成，不允许手工编辑。它是仓库中最大的文本文件，因此每次账本变动都表现为一个大 diff；这是已知代价。

有两条判据是环境感知的，会自行跳过并打印原因：源码与运行副本比对，以及 `defineTool` 契约检查。正是这些跳过使"在干净克隆上可运行"成立，而不是一个假设。
